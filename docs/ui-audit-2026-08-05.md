## Verdict

Two distinct problems, and the copy one is the *less* serious of the two.

**Copy.** The dominant defect is a single pattern repeated ~20 times: a statement,
an em dash, then unrequested reasoning. The archetype is
`ProjectForm.jsx:185` — *"The customer can't be changed after creation — create a
new project instead, so the delivered/promised history stays with the right
account."* Ten of the thirty-odd copy findings are **deletions, not rewrites**,
because the reasoning is already in the file's own header comment. `ProjectDetail.jsx:6-8`
states the work-log rationale that line 418 repeats to the user; `WorkLogForm.jsx:3-7`
states the Tidy-up rationale that line 175 repeats. The comment already carries the
load — the UI text is duplication.

**Accessibility.** Worse, and not a matter of taste:

- **36 form controls, 0 with an `id`.** The `Field` helper (copied into three
  forms) renders `<label>` as a sibling with no `htmlFor`, so every input, select
  and textarea in New Project, Edit Project, Add Item and Log Work is announced as
  "edit text, blank". The two checkboxes *are* wired correctly, so the fix pattern
  already exists in the codebase.
- **41 `<th>` cells, 0 with `scope`. 6 tables, 0 with an accessible name.** One
  table (`Projects.jsx:368`) ships with **no header row at all** — eight anonymous
  columns.
- **Every link in the tracker is identified by hue alone**, and the hue fails
  contrast (3.77:1).
- **A reachable false statement.** `Timeline.jsx:341` can tell a consultant
  *"Nothing recorded for this customer in any of the sources"* about an account
  that has history. This is a bug, not copy — see C1.
- **Deleting a logged work entry has no confirmation** and rewrites the project's
  efficiency numbers.

Worth noting from the research: the 2026 report found em dashes are no longer
diagnostic of AI writing in general — **but of the major models, only Claude used
them more often than human writers**, and "more verbose with caveats" is its
documented signature. The pattern you flagged is the house style of the thing that
wrote it.

Microcopy is defined as **fewer than three sentences**. Anything longer isn't
microcopy; it's documentation in the wrong place. **10 of the 12 form hints** in
the tracker exceed the 15-word inline limit.

## 2. Critical findings

### C1 · A reachable false statement about the customer's history
`Timeline.jsx:307,318,341` — **bug, not copy**

The filter seeds with all 7 kinds regardless of whether they have events. The
"don't let them deselect everything" guard only fires when the set is *completely*
empty, but zero-count kinds stay selected. So on an account whose history is mostly
one source, deselecting that one chip leaves six empty kinds selected and the page
says **"Nothing recorded for this customer in any of the sources."**

Compounding it: the zero-count chips are `disabled`, but `s.chip` sets an explicit
white background that overrides the browser's disabled greying — so an unavailable
chip is pixel-identical to an available one, and its `title` explanation is
unreachable by keyboard (a `disabled` button isn't focusable).

- [ ] Render only kinds with `counts > 0`; drop `disabled` and `title`
- [ ] Split the two states: `Nothing recorded for this customer yet.` vs
      `No events match the selected sources.` + a **Show all** button
- [ ] Make the last-chip toggle a visible no-op (`if (!next.size) return prev;`)
      rather than silently re-selecting all seven

### C2 · 36 form controls, none labelled
`ProjectForm.jsx:24-32`, `ItemForm.jsx:12-20`, `WorkLogForm.jsx:18-26`, `WorkLogForm.jsx:142`

See Batch 3. Highest-severity finding in the audit.

### C3 · Deleting a logged work entry has no confirmation
`ProjectDetail.jsx:155-158,459`

Hours plus a markdown write-up, gone on one click, no undo — and because those
hours feed hours-efficiency and reliability, it silently rewrites the project's
ratings.

- [ ] `if (!window.confirm(\`Delete this entry? ${formatHours(entry.hours)}h logged on ${entry.workDate} will be removed.\`)) return;`

Two more unconfirmed destructive actions: `Projects.jsx:193` **Reset sample data**
destroys every local edit the banner directly above it just described; and
`WorkLogForm.jsx:149` **Reset to template** discards a pasted-and-tidied write-up.
`confirm(` count across all 14 files: **0**.

### C4 · The three clickable rows are mouse-only
`Projects.jsx:281`, `Projects.jsx:373`, `CustomerPage.jsx:325` — see Batch 2.

Worth knowing: this is a **house pattern, not a tracker bug**. The same
`<tr onClick>` appears in 11 tables app-wide, including `PsOverview`, `Handoffs`,
`CallPrepBook`, `AdminInsights`, `Registry`, `DependencyView`, `GrrAccountTable`
and `NetSaasAccountTable`. Fixing it as a shared pattern improves the whole app.
There is also **not a single `:focus-visible` style anywhere in `builder/`** — the
only precedent for pseudo-class styling is one inline `<style>{CSS}</style>` block
in `CallPrepAccount.jsx`, which is the vehicle any focus-ring fix has to use.

### C5 · The per-account table has no header row
`Projects.jsx:368` — eight columns, no `<thead>`. See Batch 3.

### C6 · Filter state is invisible to assistive tech
`Timeline.jsx:326-334` — 7 toggle chips, selected state conveyed by colour and
font-weight only, no `aria-pressed`, no group label.

- [ ] `<div style={s.controls} role="group" aria-label="Filter timeline by source">`
- [ ] `aria-pressed={kinds.has(kind)}` on each chip

### C7 · Validation is announced to nobody
`ProjectForm.jsx:341`, `ItemForm.jsx:138`, `WorkLogForm.jsx:179` — one banner pinned
at the bottom of the form, no `role="alert"`, no focus move. *"Pick a customer."*
refers to a field ~15 fields above it. See Batch 3.

### C8 · Focus is dropped when an inline form opens or closes
`ProjectDetail.jsx:283,369,425-435` — the button that had focus unmounts itself, so
focus falls to `<body>` and a keyboard user is dumped to the top of the document.

- [ ] Focus the first field on mount; return focus to the entry container on unmount

## 4. Terminology dictionary — decisions needed

Four concepts have multiple names; two are genuinely ambiguous rather than untidy.

### The two real ambiguities

**"Promised" means three things**, two of them 80 lines apart on the same screen:
`ProjectDetail.jsx:235` labels an *item count* "Promised"; `ProjectDetail.jsx:315`
labels *hours* "Promised"; `EfficiencyPanel.jsx:109` labels the *on-time outcome*
"Promise". These are the numbers you'd report upward.

> Proposed: **Promised hours** (per item) · **Quoted hours** (project budget) ·
> **Promised items** (count) · **Commitment** (the on-time column)

**"Session" means two different objects**: a work-log entry
(`WorkLogForm.jsx:67,132`) and an Alocet billed time entry
(`KIND_LABELS.session = 'Billed sessions'`).

> Proposed: **Entry** for the work log; **Billed session** stays as-is.

### The tidy-ups

| Concept | Variants in use | Proposed |
|---|---|---|
| The person | Owner · Rep · Consultant · Author · Logged by | **Owner** for assignment; **Logged by** for work-log authorship only; **Consultant** only for the roster entity |
| The customer | Customer · Account (interleaved — `ProjectForm.jsx:184-186` uses both in one field) | **Customer**; "account" only for the raw `#{id}` token |
| The work unit | Work item · Task — *and* `Task` is one of five `ITEM_TYPES` values | **Work item**; `Task` strictly a type value |
| Efficiency | Eff · Hours eff · Hours efficiency · Efficiency | **Hours eff** in headers, **Hours efficiency** in cards |
| Reliability | Reliability · Delivery reliability | Same rule as above |

### Button labels

- Create/add is worded four ways: `+ New project`/`Create project`,
  `+ Add item`/`Add item`, `+ Log work`/`Log work`, `+ New rep`/`Add rep`.
  → toggle `+ New X`, submit `Create X`.
- **`Cancel` appears twice at once.** With the item form open, `ProjectDetail.jsx:275`
  and `ItemForm.jsx:144` render two "Cancel" buttons ~80px apart. → toggles read `Close`.
- Three `Save …` variants → `Save changes`.
- The pre-call brief route has **three labels and two element types**, two of them on
  the same page. → `Pre-call brief`, always an anchor.
- `← Projects` vs `← Project` (one letter apart, different destinations) → `← Back to project`.

### Empty states

21 absence states; **5** hit the target shape (what's missing + what to do), **9**
explain pipeline internals. Four micro-empties describe the same absence with four
different nouns (`No transcript captured` / `stored` / `No notes on this time entry` /
`No write-up on this entry`). `Projects.jsx:237` is the model — it names the culprit
filter. Standardise on `No X yet.` + one action.

**Colour-only meaning, in order of impact:**

1. **Efficiency ratings** (8 sites) — the % is shown, but good/warn/bad is hue only.
   → append a word: `82% · over`.
2. **`<Bar>`** (2 sites) — the amber fill is the sole signal for two different
   conditions (project at risk; >90% of budget consumed). No text, no `aria`.
3. **Flag severity** — a 6px colour bar is the only severity marker; the row text
   never says "critical", though `CustomerPage.jsx:280` promises "N critical".
4. **Section-average bars** — fill colour is the only pass/fail signal.
   `info` severity uses `#d1d5db` on white: effectively invisible.
5. **Late target in the account view** (`Projects.jsx:390`) — red+bold ISO date with
   no "Nd late" text, while the board view *does* add it. Same data, one view
   accessible, one not.
6. **Palette collision** — `Timeline.jsx:51` reuses the health palette
   (green/amber/red) to mean *source family*, so a red `case` chip reads as an alarm
   when it only means "this row came from the cases table". → give timeline kinds a
   neutral ramp; reserve red/amber/green for health.

**Other:**
- Loading vs empty conflated twice: `Projects.jsx:128` renders **"no activity on
  record"** for every account on first paint, before the query returns — an
  assertion of absence made from ignorance. `CustomerPage.jsx:188` shows one
  "Loading customer…" for 11 sources, then a *failed* source renders its empty state.
- No pagination anywhere; the merged 7-source timeline is the realistic >50-row case.
- Two unlabelled `<select>`s (`Projects.jsx:225,229`).
- Heading hierarchy is flat below `h2`: every item, log entry, timeline entry,
  signal card and flag row title is a styled `div`, so AT sees ~8 headings on a page
  with 100+ visually-hierarchical items.
- `CustomerPage.jsx:53` sets its `<h1>` to 24px while `s.title` is 22px — same
  heading level, two sizes across screens.
- `ProjectForm.jsx:189` uses `disabled` on the customer field, which removes it from
  the tab order; `readOnly` + `aria-readonly` keeps it announced.
- `EfficiencyPanel.jsx:118` renders `—` when `loggedHours === 0`. Zero logged hours
  is a known fact, not missing data.

## 6. What's already good

Worth keeping, and worth not regressing during the fixes:

- **`Promise.allSettled` across 10–11 independent sources** with a per-source
  failure note, so one dead table degrades a section instead of blanking the page.
  The mechanism is right; only the wording needs work.
- **Loading, empty and error are three distinct states** in `ProjectDetail.jsx:160-173`
  and for the lazily-loaded transcripts (`idle`/`loading`/`loaded`/`error`) — no
  "no results" while still fetching.
- **Form fundamentals**: labels above inputs, no placeholder-as-label anywhere,
  validation on submit not per keystroke, values survive a failed submit, primary
  before cancel, native date pickers throughout.
- **Disabled submit buttons always swap their label to `Saving…`** — no greyed
  control ever reads as broken.
- **`formatDue()`** turns bare ISO into `in 4d` / `3d late` / `today`, and returns
  `late` as a separate boolean so lateness is carried by a word, not only by red.
  The per-task `Promise` column follows the same rule — which is exactly why the
  colour-only headline numbers above it stand out.
- **`—` vs `0` is deliberate and mostly correct**: `—` for unknown, muted `0` for a
  real zero. Two violations, both listed above.
- **Numerics are right-aligned tabular mono** in every table. No misalignment found.
- **`Skipped` audits are excluded from every average**, so a declined score can't
  read as a catastrophic call.

## 7. Suggested order

1. **C1** (the false statement) — it's a bug, and it's cheap.
2. **Batch 1** (recolour) — biggest ratio of instances to edits, zero behaviour risk.
3. **Batch 3** (`Field` + tables) — the accessibility floor.
4. **C3** (delete confirmation) — one line, prevents data loss.
5. **Batch 2** (real navigation) — do it as the shared pattern so the other 8 tables
   in the app benefit.
6. **§3 copy cuts** — mostly deletions; safe to do in one pass.
7. **Batch 4** (terminology) — after you've picked the words in §4.
8. **Batch 5** (style consolidation) — last, but it's what stops Batch 1 re-drifting.

Everything in §3 and §4 is a judgement call about *your* product vocabulary. The
proposals are defaults, not decisions.
