# Metrics MCP — Authentication & Access Control Options

**Context for reviewer:** We have a working MCP server (Supabase Edge Function at `supabase/functions/mcp-metrics/`) exposing 7 tools to Claude Desktop. Currently auths via hashed bearer tokens stored in `mcp_tokens`, minted manually by a Python script. Asking for a sanity check on the path to broader rollout.

## Current state

- **MCP server:** remote, HTTPS, deployed. Lives at `https://agkubdpgnpwudzpzcvhs.supabase.co/functions/v1/mcp-metrics`.
- **Auth:** per-user bearer tokens. Plaintext is `mcp_<256-bit random>`, stored only as SHA-256 hash in Supabase `mcp_tokens` table with `user_email`, `created_at`, `last_used_at`, `revoked_at`. Generated by `scripts/generate_mcp_token.py`.
- **Audit:** every tool call → row in `mcp_audit` (tool, args, token_id, latency_ms, bytes_billed, rows_returned, success).
- **Deployment target:** Anthropic Enterprise plan. Custom connectors can be added at the org level in Organization settings.
- **Identity source already available:** the builder app (`nickperaltab.github.io/method-metrics/`) has Google OAuth (commit `09eebee9`). Email is known when the user visits.

## Users we're optimizing for

- Pilot: 2–3 internal technical staff (done, working)
- Next: ~10 mix of technical + non-technical — CSMs, AEs, marketing, execs
- Later: possibly external (contractors, customers) — not in v1 scope

## Three options

### Option A — Keep current per-user tokens, Nic mints manually

**What it looks like for the user:** DM Nic for access → Nic runs `generate_mcp_token.py` → DMs plaintext via 1Password → user pastes into their Claude Enterprise connector UI.

**Implementation status:** already shipped.

**Pros**
- Zero additional code.
- Per-user audit attribution preserved.
- Revocation by flipping `revoked_at`.

**Cons**
- Nic-in-the-loop for every new user.
- Token distribution is out-of-band (1Password / Slack DM), which is error-prone.
- Rotation requires manual coordination.

**Cost to build further:** $0. This is "status quo."

---

### Option B — Self-service token page in the existing builder app (~3–4 hours)

**What it looks like for the user:** Visit `nickperaltab.github.io/method-metrics/mcp-token` → already signed in with Google (existing app auth) → if on allowlist, page shows **Generate my token** button → click once → plaintext shown once with copy button → paste into Claude connector UI.

**What we'd build**
1. **New table:** `mcp_allowlist` — `{id, email, added_at, added_by, notes}`. Nic (or anyone with service role) maintains it. Simple SQL adds/removes.
2. **New edge function:** `mint-mcp-token`. Accepts the user's Google ID token (signed JWT), verifies it against Google's JWKS, extracts email, checks `mcp_allowlist`, mints a token, inserts hashed row into `mcp_tokens`, returns plaintext once.
3. **New route in builder:** `/mcp-token` page. Uses existing `useUser()` context (already Google-authenticated), calls the edge function, displays result.
4. **Docs:** one-page "How to connect" with screenshot of the Claude connector UI.

**Pros**
- Zero Nic bottleneck after the allowlist is set up.
- Still per-user tokens, so audit/revocation unchanged.
- Reuses existing OAuth in the app — no new auth surface.
- Access control is a Postgres row insert — no UI needed for Nic initially.

**Cons**
- User still has to paste a token string once, ever.
- Token never rotates automatically (acceptable for a 90-day-ish cadence, but it is a thing).
- If allowlist gets large, editing it as SQL becomes tedious — eventually wants a tiny admin UI.

**Why not just skip the token and have the user sign in with Google every session?** — Because Claude Desktop's connector auth is "send this header on every request." Claude doesn't do the Google OAuth dance itself unless the server speaks full MCP OAuth 2.1 (see Option C). So the bearer token is how we bridge "user already signed in" to "Claude can authenticate on their behalf."

**Cost breakdown:**
- `mcp_allowlist` migration: 15 min
- `mint-mcp-token` edge function: 45 min
- `/mcp-token` route + UI: 45 min
- Allowlist check + copy-button UX: 30 min
- Docs + testing: 1 hr

Realistic total: **~3–4 hours**.

---

### Option C — Full MCP OAuth 2.1 with Google SSO (~2–3 days)

**What it looks like for the user:** Click **Connect** on the Method Metrics connector in Claude → browser opens → signs in with Google (if not already) → done. Never sees a token. If they leave the company / aren't on allowlist, Connect fails silently or shows a friendly error.

**What we'd build**
1. **OAuth 2.1 authorization server** endpoints on our edge function (per the MCP spec, roughly RFC 8414 + RFC 7591):
   - `/.well-known/oauth-authorization-server` — discovery metadata
   - `/register` — Dynamic Client Registration (returns `client_id`)
   - `/authorize` — starts the flow; redirects user to Google (via Supabase Auth or directly)
   - `/token` — exchanges code → our JWT
2. **Our own JWT format** — short-lived access token (1h), refresh token (30d). Signed with a secret in Supabase edge function env. Payload: `{email, token_id, exp}`.
3. **Allowlist enforcement** at `/token` time: don't issue a JWT unless email ∈ `mcp_allowlist`.
4. **`verifyBearer` swapped** to JWT verify + allowlist re-check (defense in depth).
5. **Refresh token handling** — so user's session survives the 1h access token expiry.

**Pros**
- Closest to a consumer-grade flow. User clicks Connect and it just works.
- No token exposure anywhere — nothing to leak, nothing to paste.
- Natural revocation: removing someone from `mcp_allowlist` blocks them at next token refresh (within 1h).
- Matches how Linear / Notion / GitHub MCPs work.

**Cons**
- Meaningfully more code to maintain.
- OAuth 2.1 + DCR has subtle correctness/security requirements; hand-rolling is where most MCP servers get CVEs.
- Debugging OAuth flows in Claude Desktop is harder than debugging a bearer header (fewer observable states).

**Cost breakdown (rough):**
- OAuth discovery + DCR endpoints: 4 hr
- `/authorize` + Google redirect (via Supabase Auth): 4 hr
- `/token` + JWT issuance + refresh: 4 hr
- Swap `verifyBearer` → JWT verify: 2 hr
- Allowlist table + integration: 1 hr
- End-to-end testing with Claude Desktop: 4 hr
- Docs + error UX: 2 hr

Realistic total: **~2–3 days.**

**Shortcuts we evaluated and rejected:**
- *Use Supabase Auth as the OAuth provider directly* — Supabase Auth doesn't expose OAuth 2.1 authorization server endpoints in the exact shape Claude's MCP client expects (it's designed for first-party web apps, not as a pluggable OAuth AS for third-party clients). We'd still need to wrap it.
- *Use WorkOS / Auth0* — adds a paid dependency and a new vendor; overkill for ~10 users.

## Option comparison at a glance

| Dimension | A: manual tokens | B: self-service page | C: full OAuth |
|---|---|---|---|
| User setup effort | Ask Nic → paste token | Visit page → paste token | Click Connect |
| Nic effort per user | 1 min (mint + DM) | Add email to allowlist | Add email to allowlist |
| Build cost | 0 (done) | ~3-4 hr | ~2-3 days |
| Ongoing maint | Manual rotation | Allowlist updates | OAuth correctness risk |
| Per-user audit | ✅ | ✅ | ✅ |
| Token exposure surface | 1Password + DM + user's machine | User's machine | Never in user hands |
| Appropriate scale | 2–5 | 5–30 | 30+ / public / external |

## My recommendation (non-binding)

**Jump to Option B.** It's a half-day and it moves Nic out of the critical path. It preserves everything we like about Option A (per-user tokens, audit, revocation) and eliminates the biggest friction point (manual distribution).

**Defer Option C** until one of:
- We cross ~30 users
- We open it to people outside Method
- A user complains about re-pasting tokens after rotation (won't happen for 90+ days)
- We want to productize this for external customers

## Specific things I want the reviewer to poke at

1. **Is there a simpler way to get the user's email to the MCP server that I'm missing?** E.g., does Anthropic Enterprise pass any user identity metadata in requests to custom connectors that I could use instead of tokens entirely?
2. **On Option B, is storing Google ID tokens (briefly, for verification) in an edge function OK?** Or should the flow use Supabase Auth's own session JWT instead of a raw Google ID token?
3. **On Option C, is there an existing library (Deno-compatible) that implements MCP OAuth server endpoints?** I haven't found one. If one exists, it could shave a day off the estimate.
4. **Token rotation policy** — should tokens expire automatically (say 180d)? Our current design lets them live indefinitely until revoked. Security tradeoff vs. UX.
5. **Allowlist vs deny-list** — I've assumed allowlist (must be on list to get in). Any reason to go deny-list (anyone @method.me, unless specifically blocked)?
